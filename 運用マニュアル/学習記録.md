# 学習記録｜GitHubへ追記保存

## 共通形式（既存Phase 2互換）
`演習ログ/記録/{sequence:08d}-{UUID}.md`に、新しいイベント1件を保存する。既存ファイルの削除・更新はしない。本文に必ず以下の形のJSONブロックを1つ置く。

````text
# 学習記録｜イベント種別

日時：ISO8601（+09:00）

区画：実在の区画ID

```json
{
  "id": "UUID",
  "at": "ISO8601（+09:00）",
  "sequence": 1,
  "type": "start",
  "request_id": "sessionUUID-start",
  "payload_sha256": "kindとpayloadから求めたSHA256",
  "payload": {}
}
```
````

サンプル中の仮値を実学習として保存しない。sequenceは既存イベント数+1で開始し保存バッチ内で加算する。idはUUID、request_idは英数字・ハイフン・下線の1〜100文字。再送でも同じID・request_idを使う。

payload_sha256は既存engine.pyと同じPythonの `hashlib.sha256(json.dumps([kind,payload],ensure_ascii=False,sort_keys=True).encode()).hexdigest()`。JSON区切りの空白も既定値を使う。実行環境で厳密なハッシュ計算ができない場合は値を捏造せず、未保存のpayload一式をWorkへ渡して計算・保存する。新たなローカルアプリは作らない。

| type | payloadの必須内容 |
|---|---|
| start | unit_id, questions（採用問題の完全スナップショット。答え・根拠・版を含む） |
| submit | session_id（startイベントid）, unit_id, answers（全採用問題IDに対する選択添字配列または自由記述文字列） |
| assessment | session_id, unit_id, scores（自由記述ID:0/0.5/1）, method="self_rubric" |
| question_revision | questions（既存形式）, reason |
| question_report | question_id, version, reason |
| session_checkpoint | session_id, unit_id, current_question_id, phase, answers, scores, question_refs, additional_questions, unresolved |
| session_pause | session_id, unit_id, reason |
| session_complete | session_id, unit_id, weak_topics, unresolved, self_understanding, completion_text, next_review |

補助イベントは既存JSON外枠を共用する。学習マスターのinitialは履歴保護用で上書きしない。問題のスナップショットと追加質問の保存は独自作成した内容・要旨に限定し、PDF本文の長文転載をしない。

## 保存と競合確認
1. 終了・保存のユーザー指示を根拠に対象リポジトリへ保存する。他リポジトリの承認を流用しない。PC同期の安全条件が既に確認できていれば繰り返し聞かない。PC未確認の場合も、一意な新規ログのみ作成し既存ビューを更新しない。
2. main headと最新tree、既存ログを再取得。同じrequest_idがあればpayload_sha256と中身を比較し、一致なら再保存せず既存結果を返す。不一致なら上書きせず停止。GitHub以外の未保存ログが分かる場合は重複を照合する。
3. 新規ログの名前に衝突がないこと、区画ID・問題ID・版・session_idの参照を確認。新規イベントのsequenceは最新一覧に基づく連番にする。
4. 書込みツールが使える環境では、最新base treeへ新規ログを追加し、親commitを開始時headにしてcommitを作り、mainをexpected_sha付き・force=falseで更新する。一括処理できない場合はcreate_fileで新規ファイルだけ作り、成功したrequest_idを記録し残りだけ再送。途中失敗を全件成功と報告しない。
5. headが変化していたら再取得。ログ以外の意図しない変更・内容競合は停止。別セッションのログ追加だけなら最新headで重複確認しsequenceを再計算して新規追記を再試行。force pushしない。
6. 更新後のcommit SHAをrefに保存した各ログを再取得。完全なUTF-8本文・JSON・SHA256・イベント数・参照先を一致検証し、mainがそのcommitを含むことを確認。一覧やcommit成功だけでは内容検証済みとしない。
7. 失敗時は未保存または部分保存と報告し、同じrequest_idを持つ未保存イベントだけを渡す。保存済みログを削除してやり直さない。

## 書込み不可の通常チャット
実行環境にファイル作成ツールがなければ、書込み不可と表示し、上記互換のイベントMarkdown一式と保存先を提示する。ユーザーがWorkへ「この未保存ログを同じrequest_idで重複確認して保存」と渡すか、GitHub画面から新規ファイルとして追加する。次回は再取得できたログのみ保存済み履歴に含める。

## ChatGPTで追加収集する学習メタデータ（2026-10-20）
選択式の正誤と、解説後の「復習必要性1〜5」は別々に記録する。復習必要性は本人が実際に送信した値だけを記録し、未回答を推定で埋めない。旧来の「理解度1〜5」とも区別し、既存Phase 2の理解度算出・assessment(scores:0/0.5/1)に置換しない。

追加質問・自由回答に記載された「正答したが自信がない」「用語を説明できない」「誤選択肢の理由がわかる」などの学習所見や、出題形式・難易度表示への改善要望は、checkpointの追加メタデータまたは別途許可された新規イベントのpayloadに保持できる。既存の必須キーとイベント形式を変えず、既存ファイルは上書きしない。

暫定代替問題を使った場合は、正式なquestion_id/versionと混同せず、代替識別子・問題文・選択肢・正解・実回答・検証状態・代替理由を明記する。元のtext問題は未回答として残し、代替の正答を元問題の正式submitへ黙って移植しない。実演中の改善提案をマニュアルへ反映する操作と、区画完了・学習成績のsubmitは別操作とする。
